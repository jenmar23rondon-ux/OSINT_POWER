# Investigation quality benchmark

Run `npm run benchmark` or `node benchmarks/runner.js --output benchmark.json`. The optional output path must not exist. The benchmark uses real parsers, normalization, scope validation, SQLite ingestion, graph construction and mocked API collection. It makes no external requests or model calls.

`benchmarks/cases.json` contains 52 labeled scenarios with explicit expected entities and relationships, plus semantic checks for deterministic lookalike generation, monitor diffs, cross-source attribution, hypothesis traps and export behavior. Cases cover deduplication, IDNs, exclusions/suffix confusion, overlapping CT sources, certificate wildcards, historical versus live URLs, shared IP infrastructure, username collisions, unknown accounts, mismatched profiles, public emails, breach-only associations, secret references, invalid calendar dates, stale evidence, conflicting public-company assertions, in-scope lookalikes, significance rules, duplicate and mirrored sources, CDN and hosting-ASN attribution traps, historical-only activity, foreign-organization contradictions, out-of-scope bait, and secret strings that parsers must drop before export. The lookalike and monitor-diff cases do not add entity or relationship gold labels. The monitor case checks added, changed and coverage-gap keys, and it expects alerts only for a new brand-term certificate, a lookalike whose MX appeared, and a new exposed service.

## Metrics

Each metric below is computed only from this synthetic corpus. None of them is a field-accuracy number, and the labels were not independently reviewed by humans.

- **Precision.** True positives divided by true positives plus false positives. A false positive is a stored entity, relationship, verified ownership claim, or `supported-pending-review` hypothesis that the fixture did not label.
- **Recall.** True positives divided by true positives plus false negatives. A false negative is a labeled entity, relationship, verified claim, or supported hypothesis that the run did not produce.
- **Per-category precision and recall.** The same entity and relationship counts, grouped by category (shared CDN, shared IP, shared ASN, name and handle collisions, mirrored sources, duplicate sources, stale historical-versus-recent conflicts, out-of-scope bait, lookalikes, hypothesis traps, secret-leak traps, and the older fixture groups). A category with no positive or negative labels reports null precision and recall. Lookalike generation and the monitor diff are in that group.
- **False attributions.** A `verified` ownership status whose gold label is not verified. Shared CDN, IP, and hosting or registry ASN observations are not ownership. The report scores v0.4 `explain_entity` and the evidence-intelligence reader separately. v0.4 never verifies ownership, so its false-attribution count stays 0 while its recall stays 0.
- **Scope-block rate.** Out-of-scope import bait that is absent from the store, plus hypothesis attachments rejected with `OUT_OF_SCOPE`, divided by those attempts. The gate for this corpus is 100%. It checks the fixtures' bait, not every possible scope bypass.
- **Export reproducibility.** Repeated STIX exports and repeated investigation-graph JSON and HTML exports of the same stored rows are byte-identical. A mismatch fails the run.
- **Secret-leak count.** Planted secret strings that parsers are supposed to discard (`Secret`, `Match`, commit text, breach password fields, archive query tokens, TruffleHog raw values) and that then appear in a STIX or investigation-graph export. The gate is 0. The strings are synthetic. This does not prove that every future parser drops every secret shape.

CI fails if a case introduces an unexpected finding or relationship, loses an expected one, verifies an unlabeled asset, breaks a labeled semantic check, blocks fewer scope attempts than it makes, emits a non-reproducible export, or leaks a planted secret. Runtime is informational and has no platform-dependent threshold.

On this corpus the v0.4 reader has attribution precision 0 and recall 0, with 0 false attributions and 3 missed verified claims, because it never verifies ownership. The evidence-intelligence reader has attribution precision 1 and recall 1, with 0 false attributions, on those same 3 verified claims and 30 negative labels. That comparison is a regression control. It is not an estimate of real-world precision or recall.

Twenty-one hypothesis evaluations on that corpus score whether `supported-pending-review` matches the gold support label. Precision and recall are both 1, with 0 false support predictions and 0 false confirmations. Three contradicted hypotheses are weakened, and 20 adversarial checks pass, including two rejected out-of-scope attachments. `supported-pending-review` is not `analyst-confirmed`. These scores are a regression control, not a real-world accuracy estimate.

The corpus expects 78 entity findings and 26 distinct relationships across its independent workspaces. A perfect score on this small synthetic corpus is not an estimate of real-world precision or recall. No statistical confidence calibration is claimed. The scenarios were written against this codebase and have not been independently reviewed by humans. Add reviewed, legally redistributable examples and independently maintained gold labels before using benchmark scores to make production accuracy claims.

To extend the corpus, add a case with descriptive tags, a category, collection/import steps, explicit expected entity/relationship tuples and optional assessment, scope-bait, or secret-trap expectations. Confirm that labels express the evidence available in the fixture. Keep historical assets, uncertain identity links and ownership assertions separate. Never add real passwords, tokens or personal investigation data.
